# 运行日志与故障上报 · 设计

编制日期：2026年9月20日

## 1 目标

服务器出问题时（进程崩溃、接口 500、启动失败、授权或额度异常），自动留下足够排查的记录，并可按需打包上传到**私有**日志仓库，让开发侧直接从 GitHub 拉取分析，而不必让使用者手工复制粘贴日志。

**默认不上传**：只有显式配置了日志仓库与令牌才启用；未配置时只在本机留存诊断包。

## 2 运行日志

- 应用日志写入 `data_dir/日志/app.log`，按大小轮转（默认 5 MB × 5 份）。级别默认 INFO，可用 `INVOICE_SORTING_LOG_LEVEL` 调整。
- 记录内容：启动与配置摘要（不含密钥）、每个 5xx 的请求方法与路径、异常堆栈、后台任务失败、收件箱导入失败、授权校验结果、额度拦截。
- **不记录**：请求体、文件内容、密码、会话 Cookie、授权密钥（只记密钥指纹前后 4 位）。
- 4xx 属于正常的用户操作反馈，不进错误日志，避免噪音。

## 3 诊断包

`invoice-sorting diagnose [--upload] [--reason=crash|manual|error]` 生成 zip：

| 内容 | 说明 |
| --- | --- |
| `summary.json` | 应用版本、Git 提交、部署形态、Python 与系统版本、启动时间、磁盘剩余、内存、账套数与记录数量级（不含具体数据） |
| `app.log` | 应用日志尾部（默认最近 2000 行） |
| `journal.log` | `journalctl -u invoice-sorting -n 500`（有 systemd 时） |
| `service.txt` | systemd 状态、重启次数 |
| `nginx-error.log` | Nginx 错误日志尾部（存在且可读时） |
| `env.txt` | 相关环境变量名与是否设置（**只写“已设置/未设置”，不写值**） |
| `health.json` | `/api/health` 与 `/api/license/status` 的返回（去掉实例标识） |

包名 `diag_<主机短名>_<时间>_<故障指纹前8位>.zip`，落在 `data_dir/日志/诊断包/`，只保留最近 10 个。

## 4 脱敏

上传前对所有文本做规则替换（本机留存的包也同样脱敏，避免误发）：

| 类型 | 处理 |
| --- | --- |
| 文件名（发票、凭证原件） | 保留扩展名与类型词，其余替换为 `<文件名>` |
| 商家名、销售方、入住人、用户名与显示名 | `<名称>` |
| 金额、发票号码、订单号、银行卡尾号、税号 | `<数字>`、`<发票号>` 等占位符 |
| 邮箱、手机号、身份证号 | `<邮箱>`、`<手机号>`、`<证件号>` |
| IP 与主机名 | 内网地址保留网段形态（如 `192.168.x.x`），公网地址替换 |
| 授权密钥、令牌、Cookie、密码 | `<已隐去>`（匹配 key/token/secret/password/cookie 等键名与常见格式） |
| 绝对路径中的用户名 | `/home/<用户>/…` |

脱敏是**白名单式保留**：堆栈里的模块路径、异常类型、行号、SQL 语句结构（不含参数值）保留；其余可疑串按规则替换。脱敏后包内做一次自检（正则扫描是否残留邮箱、卡号等），发现残留则拒绝上传并在日志中说明。

## 5 触发方式

1. **手工**：`invoice-sorting diagnose --upload`。
2. **崩溃**：systemd 单元 `ExecStopPost=` 在非正常退出时调用，`--reason=crash`。
3. **运行中错误**：同一故障指纹（异常类型 + 堆栈顶部位置）在 10 分钟内累计 ≥ 3 次时触发一次。
4. **限流**：同一指纹每天最多上传 1 次，全实例每天最多 5 次；崩溃重启循环不会刷爆仓库。

## 6 上传

- 配置：`INVOICE_SORTING_LOG_REPO`（如 `用户名/Invoice-sorting-logs`，**私有仓库**）、`INVOICE_SORTING_LOG_TOKEN`（细粒度 PAT，只给该仓库 Contents 写权限）、可选 `INVOICE_SORTING_LOG_BRANCH`（默认 `main`）、`INVOICE_SORTING_LOG_ENABLED`（默认按是否配齐前两项）。
- 方式：GitHub Contents API `PUT /repos/{repo}/contents/logs/<实例名>/<日期>/<包名>.zip`，base64 上传，附提交说明（故障指纹与版本）。
- 令牌只从环境变量读取，不落库、不进日志、不进诊断包；上传失败只记日志并保留本地包。
- 大小上限 5 MB（超出先截断日志再打包）；超时 30 秒，最多重试 2 次。
- 每次上传后在日志中记录仓库内路径，便于开发侧直接定位。

## 7 开发侧取用

仓库结构：

```
logs/<实例名>/<YYYY-MM-DD>/diag_xxx.zip
logs/<实例名>/latest.json     最近一次故障的指纹、版本、时间与包路径
```

开发时只需：拉取该私有仓库 → 解压最近的包 → 看 `summary.json` 与 `journal.log`。

## 8 安全与隐私

- 仓库必须为私有；代码中不做“默认仓库”兜底，配置缺失就不上传。
- 令牌权限最小化（单仓库 Contents 写），可随时吊销；文档提示定期轮换。
- 上传属于把数据发往外部服务：首次启用时在日志与运营后台显著提示，并在 README 中说明“上传内容、脱敏范围与关闭方法”。
- 关闭方式：清空 `INVOICE_SORTING_LOG_REPO` 即停止上传，本地诊断包不受影响。
