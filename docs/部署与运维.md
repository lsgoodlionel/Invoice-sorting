## 一、三种部署形态

| 形态 | 适用场景 | 部署方式 | 关键配置 |
| --- | --- | --- | --- |
| **本机自用** | 一个人在自己电脑上用 | `scripts/setup.sh` 后直接启动 | 全部默认即可 |
| **私有化单账套** | 一个团队 / 一家客户独占一套服务 | Ubuntu 一键脚本或 Docker | `DEPLOY_MODE=single`（默认），可选授权密钥 |
| **SaaS 多账套** | 一套服务承载多个客户（账套） | Ubuntu 一键脚本或 Docker | `DEPLOY_MODE=saas` |

三种形态**是同一套代码、同一条安装命令**，只靠环境变量区分：

- `single`（默认）：界面里完全不出现“账套”概念，行为与老版本一致。业务数据仍在数据目录根部（`invoice.db`、`文件库/`…），老部署升级后文件不搬家。
- `saas`：一套服务多个账套，每个账套有独立的数据库与文件目录（`tenants/<账套标识>/`），账号、套餐、用量集中在控制库 `control.db`。

> 不确定选哪个？选 `single`。以后要转成 SaaS，可以用[账套搬迁](#八账套搬迁)把数据导入到 SaaS 里，反之亦然。

## 二、本机自用

macOS / Linux，需要 Python 3.12 与（本地构建前端时的）Node.js 20+：

```bash
git clone https://github.com/lsgoodlionel/Invoice-sorting.git
cd Invoice-sorting
scripts/setup.sh
backend/.venv/bin/invoice-sorting
```

浏览器会自动打开 `http://127.0.0.1:8765`。数据默认在 `~/InvoiceSorting`。

只有自己一个人用、不想每次登录时：

```bash
INVOICE_SORTING_AUTH_ENABLED=false backend/.venv/bin/invoice-sorting
```

## 三、私有化单账套（服务器）

适用于 Ubuntu 22.04 / 24.04。**安装与升级是同一条命令**，重复执行即升级。

### 3.1 最简安装

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh | sudo bash
```

完成后访问 `http://服务器IP:8765`，首次打开网页为管理员 `admin` 设置初始密码。

### 3.2 带域名与 HTTPS

域名需已解析到这台服务器，且 80 / 443 端口可访问：

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo DOMAIN=invoice.example.com ENABLE_HTTPS=true EMAIL=ops@example.com bash
```

### 3.3 带授权密钥（需要定期在线校验的交付）

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo DOMAIN=invoice.example.com ENABLE_HTTPS=true EMAIL=ops@example.com \
         LICENSE_KEY=替换成供应商提供的密钥 \
         LICENSE_SERVER=https://saas.example.com bash
```

- 密钥写入 systemd 单元 `/etc/systemd/system/invoice-sorting.service`，配置了密钥时该文件权限收紧为 `600`。
- **升级时不需要再带这些变量**：脚本会自动沿用单元文件里已有的值，不会把已配置的密钥覆盖成空。
- 确实要清空某项时，显式传空值，例如 `| sudo LICENSE_KEY= bash`。

### 3.4 不带授权密钥

`LICENSE_KEY` 与 `LICENSE_SERVER` 任意一项为空时，程序**完全不做授权校验、也不发起任何网络请求**，与现在的行为一致。

## 四、SaaS 多账套

### 4.1 安装

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo DEPLOY_MODE=saas DOMAIN=app.example.com ENABLE_HTTPS=true EMAIL=ops@example.com bash
```

安装命令里**不需要任何账号、密码信息**。装完后用**主域名**（不带账套子域名）打开网页，
第一次进入就能设置**首个平台管理员**的用户名（默认 `admin`）与密码，设置完即登录，
左侧导航出现「平台」入口，可以直接开通账套。

账号统一在登录页登录，登录后按账号归属定位账套；一个账号属于多个账套时可在界面切换。

### 4.2 可选：账套子域名

配置 `TENANT_HOST_SUFFIX` 后，`t1.example.com` 直接定位到账套 `t1`：

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo DEPLOY_MODE=saas DOMAIN=example.com TENANT_HOST_SUFFIX=example.com bash
```

脚本会把 Nginx 的 `server_name` 写成 `example.com .example.com`（泛域名）。还需要你自己完成两件事：

1. **DNS**：添加泛解析 `*.example.com` → 服务器 IP。
2. **证书**：子域名 HTTPS 需要 `*.example.com` 的**通配符证书**。Let's Encrypt 的通配符证书只能用 DNS-01 验证申请，一键脚本的 `ENABLE_HTTPS=true` 只会为 `DOMAIN` 申请单域名证书。通配符证书示例（需要 DNS 服务商插件）：

```bash
sudo certbot certonly --manual --preferred-challenges dns -d 'example.com' -d '*.example.com'
sudo certbot install --cert-name example.com
```

> 不配 `TENANT_HOST_SUFFIX` 也能正常使用 SaaS，只是没有“子域名直达”这一便利。

### 4.3 账套与套餐管理

账套开通、套餐、到期日、成员邀请与用量在**平台运营后台**（`/platform` 页面，仅平台管理员可见）操作。

**首个平台管理员**在网页上产生：用主域名打开网站，第一次进入即可设置用户名（默认 `admin`）与密码，
设置完自动登录并拥有「平台」入口。这一步和单账套的「首次打开网页设置 admin 密码」是同一套流程，
安装命令里始终不出现账号信息。

> 和单账套一样：设置之前，任何能访问该地址的人都可以抢先设置，装完请尽快打开页面完成。

忘记密码、或服务器上没有浏览器可用时，仍可以用命令行补一个平台管理员：

```bash
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting grant-platform-admin --username ops
```

命令会按需建号、标记为平台管理员，并确保该账号至少属于一个账套（多账套部署会自动开通一个「平台运营」账套）。之后用该账号在主域名登录，左侧导航会出现「平台」入口。

### 4.4 通知邮件（SMTP）

注册申请的审批结果（注册链接或否决原因）通过邮件发给申请人。**以网页配置为主**：平台管理员在
「平台 → 邮件」页签填写 SMTP 服务器、端口、加密方式（SSL/STARTTLS/不加密）、账号、密码（授权码）、
发件人与站点地址，保存后即时生效，无需重启；同页可「测试连接」（只登录不发信）与「发送测试邮件」
（每位平台管理员每分钟最多 3 封），失败原因按「连不上/超时、TLS 握手失败、认证失败、其他」分类显示。
页面提供 QQ 邮箱、163 邮箱、腾讯企业邮、阿里企业邮、Gmail 的服务器参数预设；大多数邮箱需使用**授权码**而非登录密码。

- **密码加密存储**：网页填写的密码用 Fernet 加密后存入控制库，任何接口都不返回密码或密文。
  密钥优先取环境变量 `INVOICE_SORTING_SECRET_KEY`（base64 Fernet 密钥，可用
  `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` 生成）；
  没配时首次保存密码会在数据目录生成 `secret.key`（权限 `600`）。密钥不入库，也不随账套搬迁包与诊断包导出。
- **密钥丢失或更换**后已保存的密码无法解开：页面提示「请重新填写 SMTP 密码」，发信记为失败，不会报 500。
  整机迁移或恢复备份时请连同 `secret.key` 一起复制（或保持相同的 `INVOICE_SORTING_SECRET_KEY`）。
- **环境变量覆盖（可选）**：`INVOICE_SORTING_SMTP_HOST` 与 `INVOICE_SORTING_SMTP_FROM` 都配置时，整套邮件配置以环境变量为准，
  网页只读显示「由服务器环境变量配置」，测试按钮仍可用。适合用配置管理工具统一下发的场景。
- **新申请提醒**：在「平台 → 邮件」填「通知接收邮箱」（英文逗号分隔，最多 5 个），有新申请待审批时会给这些地址发一封提醒（含申请摘要与后台直达链接，不含任何凭据）；留空则不发。
  环境变量覆盖模式下网页只读，改用 `INVOICE_SORTING_SIGNUP_NOTIFY_EMAILS` 配置。同一实例每小时最多 20 封，超出的跳过并记日志。
- 未配置邮件时不发信：批准或否决后，后台直接给出注册链接与可复制的通知文字，由管理员手动转告。

## 五、Docker 交付

文件都在 `deploy/docker/`：`Dockerfile`、`docker-compose.yml`、`.env.example`、`nginx.conf`。

### 5.1 快速开始

```bash
git clone https://github.com/lsgoodlionel/Invoice-sorting.git
cd Invoice-sorting/deploy/docker
cp .env.example .env
```

按需编辑 `.env`（不改也能跑，默认单账套、不校验授权），然后：

```bash
docker compose up -d --build
```

访问 `http://服务器IP:8765`。

### 5.2 前面再挡一层 Nginx

```bash
docker compose --profile nginx up -d --build
```

建议同时在 `.env` 里把应用端口收回本机：

```bash
APP_PUBLISH=127.0.0.1:18765
NGINX_PUBLISH=80
```

### 5.3 常用运维命令

```bash
docker compose logs -f app          # 实时日志
docker compose ps                   # 运行状态与健康检查
docker compose restart app          # 重启
docker compose down                 # 停止（命名卷中的数据保留）
```

在容器里执行命令行工具（重置密码、导出账套）：

```bash
docker compose exec app invoice-sorting reset-password
docker compose exec app invoice-sorting export-tenant --slug 客户A --out /data/备份/客户A.zip
```

### 5.4 镜像说明

- **多阶段构建**：前端（Node 构建或直接使用仓库里的 `frontend/dist`）+ 后端（uv 按 `uv.lock` 精确安装到 `/opt/venv`）+ 精简运行时。
- **非 root 运行**：容器内用户 `invoice`（UID/GID 10001），数据目录 `/data`。
- **不含任何密钥**：授权密钥、域名等只在运行时通过环境变量传入；`deploy/docker/.env` 已被 `.gitignore` 忽略，也被构建上下文排除。
- **健康检查**：内置 `HEALTHCHECK`，探测 `/api/health`。

构建参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `FRONTEND_SOURCE` | `build` | `build` 在容器内构建前端；`prebuilt` 直接用仓库里已有的 `frontend/dist`（需先在宿主机构建好） |
| `INSTALL_OCR` | `true` | `false` 时不装截图文字识别依赖，镜像约小 300MB |
| `PYPI_INDEX` / `NPM_REGISTRY` | 官方源 | 国内网络可换镜像源 |

```bash
# 例：用已构建好的前端 + 不装 OCR + 国内镜像源
docker build -f deploy/docker/Dockerfile -t invoice-sorting:local \
  --build-arg FRONTEND_SOURCE=prebuilt \
  --build-arg INSTALL_OCR=false \
  --build-arg PYPI_INDEX=https://mirrors.aliyun.com/pypi/simple \
  .
```

### 5.5 用宿主机目录存数据

默认用 Docker 命名卷 `invoice-data`。想直接在宿主机看到文件，在 `.env` 里写绝对路径：

```bash
DATA_VOLUME=/srv/invoice-sorting
```

容器以非 root 运行，**挂载前必须把目录授权给 UID 10001**，否则容器会启动失败并打印提示：

```bash
sudo mkdir -p /srv/invoice-sorting
sudo chown -R 10001:10001 /srv/invoice-sorting
```

## 六、配置项总表

### 6.1 应用环境变量（程序直接读取）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `INVOICE_SORTING_DATA_DIR` | `~/InvoiceSorting` | 数据目录 |

| `INVOICE_SORTING_OPEN_BROWSER` | `true` | 启动时是否打开浏览器 |
| `INVOICE_SORTING_WATCH_INBOX` | `true` | 是否监听收件箱目录 |
| `INVOICE_SORTING_FRONTEND_DIST` | `frontend/dist` | 前端构建目录 |
| `INVOICE_SORTING_AUTH_ENABLED` | `true` | 登录认证；仅本机单人使用时可设 `false` |
| `INVOICE_SORTING_DEPLOYMENT_MODE` | `single` | 部署形态：`single` / `saas` |
| `INVOICE_SORTING_TENANT_HOST_SUFFIX` | 空 | 仅 SaaS：账套子域名后缀，例如 `example.com` |
| `INVOICE_SORTING_LICENSE_KEY` | 空 | 私有化授权密钥 |
| `INVOICE_SORTING_LICENSE_SERVER` | 空 | 授权校验服务地址，只写到域名，例如 `https://saas.example.com` |
| `INVOICE_SORTING_LICENSE_CHECK_INTERVAL_HOURS` | `24` | 在线校验间隔（小时） |
| `INVOICE_SORTING_LICENSE_GRACE_DAYS` | `14` | 授权过期后的宽限天数 |
| `INVOICE_SORTING_LICENSE_PRIVATE_KEY` | 空 | **仅控制面**：签发授权令牌的 Ed25519 私钥（base64 原始 32 字节） |
| `INVOICE_SORTING_LICENSE_PUBLIC_KEY` | 内置常量 | 验签公钥；一般不配，用代码内置值 |
| `INVOICE_SORTING_LOG_LEVEL` | `INFO` | 运行日志级别（`DEBUG`/`INFO`/`WARNING`/`ERROR`） |
| `INVOICE_SORTING_LOG_REPO` | 空 | **私有**日志仓库 `owner/repo`；**留空即不上传**，诊断包只留本机 |
| `INVOICE_SORTING_LOG_TOKEN` | 空 | 细粒度 PAT，只给该仓库 Contents 读写；只从环境变量读，不落库、不进日志、不进诊断包 |
| `INVOICE_SORTING_LOG_APP` | `invoice-sorting` | 仓库内的应用命名空间（该仓库多个应用共用） |
| `INVOICE_SORTING_LOG_INSTANCE` | 主机短名 | 实例名，用于区分同一应用的多台服务器 |
| `INVOICE_SORTING_LOG_BRANCH` | `main` | 上传到哪个分支；空仓库首次上传会自动创建默认分支 |
| `INVOICE_SORTING_SECRET_KEY` | 空 | 加密网页填写的 SMTP 密码用的 Fernet 密钥（base64）；留空时自动在数据目录生成 `secret.key`（`600`） |
| `INVOICE_SORTING_SMTP_HOST` | 空 | **可选覆盖**：与 `_SMTP_FROM` 都配置时，邮件整体改用环境变量（网页只读）；一般直接在「平台 → 邮件」配置 |
| `INVOICE_SORTING_SMTP_PORT` | `465` | 同上，环境变量覆盖时的端口 |
| `INVOICE_SORTING_SMTP_USER` | 空 | 同上，登录账号 |
| `INVOICE_SORTING_SMTP_PASSWORD` | 空 | 同上，密码/授权码；不进日志与诊断包 |
| `INVOICE_SORTING_SMTP_FROM` | 空 | 同上，发件人（`地址` 或 `名称 <地址>`） |
| `INVOICE_SORTING_SMTP_TLS` | `ssl` | 同上，`ssl` / `starttls` / `none` |
| `INVOICE_SORTING_PUBLIC_BASE_URL` | 空 | 站点地址（注册链接、推荐链接用）；网页配置里未填时作为后备 |
| `INVOICE_SORTING_SIGNUP_NOTIFY_EMAILS` | 空 | 有新申请待审批时提醒谁（英文逗号分隔，最多 5 个）；只在环境变量覆盖模式下生效，否则在「平台 → 邮件」页面填写 |

授权密钥与服务地址**两项都非空**且部署形态为 `single` 时，才会启用在线校验。

### 6.2 一键安装脚本变量（`deploy/install.sh`）

| `DEPLOY_MODE` | `single` | 部署形态：`single` / `saas` |
| `TENANT_HOST_SUFFIX` | 空 | 仅 SaaS：账套子域名后缀，会写成 Nginx 泛域名 |
| `LICENSE_KEY` | 空 | 私有化授权密钥 |
| `LICENSE_SERVER` | 空 | 授权校验服务地址 |
| `CHECK_INTERVAL_HOURS` | `24` | 在线校验间隔（小时） |
| `GRACE_DAYS` | `14` | 宽限天数 |
| `LOG_LEVEL` | `INFO` | 运行日志级别 |
| `LOG_REPO` | 空 | 私有日志仓库 `owner/repo`；留空即不上传 |
| `LOG_TOKEN` | 空 | 日志仓库的细粒度 PAT（写入 systemd 单元后单元文件自动 `chmod 600`） |
| `LOG_APP` / `LOG_INSTANCE` / `LOG_BRANCH` | `invoice-sorting` / 主机短名 / `main` | 仓库内命名空间、实例名与分支 |
| `PYCACHE_DIR` | `/var/cache/invoice-sorting/pycache` | Python 字节码缓存目录（写入 systemd 的 `PYTHONPYCACHEPREFIX`），缓存损坏时可整目录删除 |

**升级时的取值顺序**：本次命令行显式传入 → systemd 单元里已有的旧值 → 默认值。所以升级只需重新执行安装命令，不必重复输入密钥和形态。

查看当前实际生效的配置与版本：

```bash
sudo systemctl cat invoice-sorting | grep Environment=
cat /opt/invoice-sorting/VERSION
```

## 七、私有化授权

### 7.1 工作方式

1. 安装时填写 `LICENSE_KEY` 与 `LICENSE_SERVER`；实例首次启动生成并持久化 `instance_id`（数据目录下的 `instance_id` 文件）。
2. 每 `CHECK_INTERVAL_HOURS` 小时向控制面 `POST {LICENSE_SERVER}/api/platform/license/verify` 校验一次，返回 Ed25519 签名的令牌（有效期、用户数上限、功能开关），本地落库。
3. 令牌到期后再宽限 `GRACE_DAYS` 天（容忍断网与续期延迟），期间界面顶部提示。
4. 宽限期满 → **只读模式**：可登录、可查看、可导出、可备份，不能新增与修改；数据不会被删除。
5. 密钥被停用或无效 → 立即只读，并说明原因。
6. 校验失败会区分“网络不可达”（继续宽限）与“授权无效”（立即生效）。

授权状态在网页「设置」页可见，接口为 `GET /api/license/status`；管理员可触发 `POST /api/license/recheck` 立即重新校验。

### 7.2 生成密钥对（正式发布前必做）

> 🚨 **安全警告：仓库里内置的是测试公钥，正式发布前必须替换。**
> 对应的测试**私钥是公开的**（在 `backend/tests/license_helpers.py` 里，为了跑测试而有意公开）。
> 只要还用内置公钥，任何人都能自己签出“合法”的授权令牌，授权校验形同虚设。
> 替换步骤见下。**本文不包含任何真实密钥，也不要把真实私钥写进任何文件或提交到仓库。**

第一步，在**离线或可信的机器**上生成一对 Ed25519 密钥（用应用自带的 Python 环境即可，已含 `cryptography`）：

```bash
backend/.venv/bin/python - <<'PY'
import base64
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey

key = Ed25519PrivateKey.generate()
private_raw = key.private_bytes(
    serialization.Encoding.Raw, serialization.PrivateFormat.Raw, serialization.NoEncryption()
)
public_raw = key.public_key().public_bytes(
    serialization.Encoding.Raw, serialization.PublicFormat.Raw
)
print("公钥（写进代码常量）:", base64.b64encode(public_raw).decode())
print("私钥（只配在控制面环境变量）:", base64.b64encode(private_raw).decode())
PY
```

第二步，把**公钥**写进代码常量 `DEFAULT_PUBLIC_KEY_B64`（文件 `backend/src/invoice_sorting/licensing/keys.py`），随版本发布。

第三步，把**私钥**只配置在 SaaS 控制面的环境变量 `INVOICE_SORTING_LICENSE_PRIVATE_KEY` 里。推荐用 systemd drop-in，文件权限 `600`：

```bash
sudo install -d -m 700 /etc/systemd/system/invoice-sorting.service.d
sudo install -m 600 /dev/null /etc/systemd/system/invoice-sorting.service.d/license-key.conf
sudo tee /etc/systemd/system/invoice-sorting.service.d/license-key.conf >/dev/null <<'EOF'
[Service]
Environment=INVOICE_SORTING_LICENSE_PRIVATE_KEY=在这里粘贴上一步生成的私钥
EOF
sudo systemctl daemon-reload && sudo systemctl restart invoice-sorting
```

Docker 控制面同理，用 `.env` 或 Docker secret 传入，**不要**写进 `Dockerfile` 或镜像。

私钥的规矩：

- 只存在于控制面运行环境，不落盘到仓库、不入库、不写日志。
- 泄露后必须重新生成密钥对、发布新版本（带新公钥）并给客户换发密钥。
- 定期轮换时，可先在新版本里换公钥，客户升级后旧令牌自然失效。

### 7.3 签发授权密钥

授权记录保存在控制面的控制库 `control.db` 的 `license_record` 表：客户名、用户数上限、有效期、状态、功能开关、绑定的实例。

平台管理员在**运营后台**（`/platform` → 「授权」页签）创建、吊销与删除授权记录。换机时需要平台管理员清空该记录的 `bound_instance_id`，否则新实例会被判为“密钥已绑定其他实例”。

---


### 暂不更换密钥时

内置的测试公钥可以先用着，但要知道风险与现状：

- 测试私钥在 `backend/tests/license_helpers.py` 中公开，**任何人都能签发这套实例认可的授权**，授权校验形同虚设。
- 只影响"防止私有化包被无限复制"这一件事，不影响功能、数据安全与登录鉴权。
- 启用了在线校验（配置了 `INVOICE_SORTING_LICENSE_KEY` 与 `LICENSE_SERVER`）而仍用内置公钥时，服务启动会在日志里打印告警，`GET /api/license/status` 的 `uses_test_key` 字段为 `true`，可据此确认是否已完成更换。
- 生成自有密钥对后，**私钥不要放进仓库或明文文件**：放进密码管理器，或用 `age`、`gpg` 加密后再存档，服务器上只以环境变量注入控制面进程。

## 八、账套搬迁

用于 SaaS ↔ 私有化互相搬迁、客户自助备份、故障恢复。搬迁包是一个 zip：`manifest.json`（应用版本、schema 版本、账套信息、校验和）+ 数据库一致快照 + 文件库 + 资料包。

命令行不依赖运行中的服务，但**必须带上与服务相同的环境变量**（数据目录、部署形态），否则会找错目录。

### 8.1 导出

服务器（单账套，可省略 `--slug`）：

```bash
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting export-tenant
```

SaaS 上导出指定账套：

```bash
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
     INVOICE_SORTING_DEPLOYMENT_MODE=saas \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting export-tenant \
  --slug 客户A --out /var/lib/invoice-sorting/备份/客户A.zip
```

| 参数 | 说明 |
| --- | --- |
| `--slug` | 要导出的账套标识，单账套部署可省略（默认 `default`） |
| `--out` | 输出 zip 路径；省略时写入 `数据目录/备份/租户导出/` |
| `--no-packages` | 不导出资料包（资料包可以再次生成，能明显减小体积） |

网页上也可以触发：账套管理员在「设置 → 备份与搬迁」点**立即备份**——备份即导出，产出同一个完整包
（整个业务数据库，含系统设置、分类、规则与记忆 + 全部附件 + 可选的资料包），下载到本机，同时在服务器上
**该账套自己的** `备份/账本备份/` 里保留最近 10 份（单账套即 `数据目录/备份/账本备份/`，SaaS 为
`tenants/<账套>/备份/账本备份/`，各账套互不可见），页面上可以列出并再次下载。
平台管理员可在运营后台导出任意账套（`/api/platform/tenants/{slug}/export`），这类包放在平台根目录 `备份/租户导出/`。

> 升级到本版本之前从网页导出的包在 `数据目录/备份/租户导出/` 里，不会自动搬到 `账本备份/`，也不会出现在新的列表中；
> 需要的话手动移动（文件名形如 `账套_default_20260921_101500_xxxxxxxx.zip`），不需要可以直接删除。
> 原来设置页的「数据库快照」（`备份/invoice_*.db`）已移除，旧文件同样可以手动清理；升级脚本的升级前自动备份不受影响。

> **单账套的账本备份带登录账号**：单账套部署下，网页「备份并下载」、`export-tenant` 与覆盖前的自动备份都会在包里带上
> `accounts.json`——本账套全部成员的用户名、显示名、角色、启用状态与**密码哈希**（不含明文密码、会话、邀请码、授权、
> 邮件设置与 `secret.key`）。**请把备份包当作敏感文件保管**（拿到包的人可以离线暴力破解弱密码）。
> 换机器时在新机器上用**整套覆盖**恢复即可把账号与密码一起带回，见 [8.5 换机恢复（单账套）](#85-换机恢复单账套)。
> 合并导入一律不导入账号：包里的人按用户名对上新机器已有的账号，对不上的建成停用的占位账号。
> **SaaS 部署的账套备份不含账号**（账号在平台的 `control.db` 里、全平台共用），平台数据库由平台管理员单独备份（9.2）。

### 8.2 导入

```bash
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
     INVOICE_SORTING_DEPLOYMENT_MODE=saas \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting import-tenant \
  --in /var/lib/invoice-sorting/备份/客户A.zip --slug 客户A
```

| 参数 | 说明 |
| --- | --- |
| `--in` | 搬迁包 zip 路径（必填） |
| `--slug` | 导入到哪个账套标识（单账套可省略，默认 `default`） |
| `--mode` | `merge`（默认）并入已有账套、自动去重；`replace` 整体替换 |
| `--no-settings` | 合并时不导入系统设置（报销抬头、地区、分类关键词、凭证规则、分类记忆冲突时保留本地）；默认以导入包为准 |
| `--dry-run` | 只打印预览，不写入 |
| `--overwrite` | `replace` 模式下目标账套已存在时才需要；覆盖前会自动备份现有数据 |

导入会校验版本与校验和，并自动补齐缺失的数据库列。

### 8.3 私有化 → SaaS

```bash
# 1) 在私有化服务器上导出（导出前建议停服务，保证没有正在写入的数据）
sudo systemctl stop invoice-sorting
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting export-tenant --out /tmp/客户A.zip
```

```bash
# 2) 传到 SaaS 服务器
scp /tmp/客户A.zip ops@saas.example.com:/tmp/
```

```bash
# 3) 在 SaaS 上导入为新账套（账套标识用小写英文/数字，例如 kehua）
sudo install -o invoice -g invoice -m 640 /tmp/客户A.zip /var/lib/invoice-sorting/备份/
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
     INVOICE_SORTING_DEPLOYMENT_MODE=saas \
```

### 8.4 SaaS → 私有化

```bash
# 1) 在 SaaS 上导出该账套
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
     INVOICE_SORTING_DEPLOYMENT_MODE=saas \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting export-tenant --slug kehua --out /tmp/kehua.zip
```

```bash
# 2) 在客户的新服务器上装好程序（单账套形态），然后停服务导入为 default
sudo systemctl stop invoice-sorting
sudo install -o invoice -g invoice -m 640 /tmp/kehua.zip /var/lib/invoice-sorting/备份/
sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
  /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting import-tenant \
  --in /var/lib/invoice-sorting/备份/kehua.zip --slug default --overwrite
sudo systemctl start invoice-sorting
```

注意事项：

- 账套标识（slug）只用小写字母、数字和连字符，导入后不建议再改。
- 默认是**合并**导入（已存在的跳过）；整体替换要用 `--mode replace`，对已有数据的账套必须显式加 `--overwrite`，命令会先自动备份。
- 合并时系统设置默认以导入包为准（只认白名单里的用户设置：报销抬头、税号、本地地区、已带明细平台、超期提醒天数，
  外加同名分类的颜色/关键词/办理路径、同位凭证规则与分类记忆）；内部版本标记与账号、授权、部署配置永不导入。
- 跨版本搬迁请先把两边升级到同一版本，至少保证导入方不低于导出方。
- 搬迁包里含全部发票原件，属于敏感数据：传输用 scp/rsync，落地后及时清理临时副本。
  单账套的包还带着登录账号与密码哈希，更要妥善保管。
- 私有化包导入 SaaS 时，包里的 `accounts.json` **不导入**（SaaS 账号是平台级的），成员请在运营后台开通。

### 8.5 换机恢复（单账套）

单账套的备份包带着登录账号与密码哈希，换机器只需要一个备份包：

1. **旧机器**：「设置 → 备份与搬迁 → 备份并下载」（或 `export-tenant --out /tmp/账本.zip`），把包拷到新机器。
2. **新机器**：按快速开始装好并启动，为 `admin` 设一个临时初始密码登录。
3. 「设置 → 备份与搬迁 → 导入」选择备份包，导入方式选**清空后整套覆盖**，核对预览里的「登录账号」分区
   （哪些账号新建、哪些同名账号会恢复为备份时的密码），输入账本名称确认。命令行等价写法：

   ```bash
   sudo -u invoice env INVOICE_SORTING_DATA_DIR=/var/lib/invoice-sorting \
     /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting import-tenant \
     --in /tmp/账本.zip --mode replace --overwrite
   ```

4. 导入完成后，同名账号（包括刚才登录的 `admin`）的密码已恢复为**备份时的密码**，当前会话失效，用备份时的密码重新登录即可；
   新机器上另建的、备份里没有的账号会被**删除**（执行导入的管理员本人除外），恢复后的账号与备份时一致。

说明：

- 恢复后必须至少有一个可用的管理员（启用中且设置了密码），否则导入在写入任何数据前就中止，并给出原因。
- 执行前照例把新机器现有数据整包备份到 `备份/覆盖前备份_*.zip`；账号写回失败时控制库回滚、账本用这份备份还原。
- 账号 id 以备份为准（保证历史记录的上传人、操作人不串）；与之冲突的保留账号（执行者本人）会换一个新 id，登录不受影响。
- 被删除账号在账本里的历史记录仍显示原姓名；命令行导入没有“执行者”，备份里没有的账号全部删除。
- 平台邮件（SMTP）密码与 `secret.key` 不在账本备份里；单账套一般不需要它们。
- 合并导入与导入到 SaaS 都**不会**导入账号。

## 九、备份与恢复

### 9.1 目录结构

单账套（含老部署，升级后位置不变）：

```text
/var/lib/invoice-sorting/
├── control.db        控制库：账套、账号、会话、套餐、用量、授权
├── invoice.db        业务库（SQLite）
├── instance_id       实例标识（授权校验用）
├── 收件箱/
├── 文件库/
├── 资料包/
└── 备份/             升级前自动备份（upgrade_*.db）、账本备份/（网页「立即备份」，最近 10 份）、租户导出/（命令行默认输出）
```

SaaS 多账套：

```text
/var/lib/invoice-sorting/
├── control.db
├── secret.key        加密网页 SMTP 密码的密钥（600；配置了 INVOICE_SORTING_SECRET_KEY 时没有），备份时一并保留
├── 备份/
│   ├── 平台/         平台数据库备份 control_*.db（运营后台「平台数据库备份」，最近 10 份）
│   └── 租户导出/     运营后台替某账套导出的包、命令行默认输出
└── tenants/
    ├── kehua/        每个账套一套，结构与上面单账套的业务部分完全一致
    │   ├── invoice.db  文件库/  资料包/  收件箱/
    │   └── 备份/账本备份/   该账套管理员网页备份的完整包（最近 10 份，只有本账套看得到）
    └── kehub/
```

### 9.2 完整备份

最稳妥的办法：**停服务 → 复制整个数据目录**。

```bash
sudo systemctl stop invoice-sorting
sudo tar czf /tmp/invoice-backup-$(date +%Y%m%d).tar.gz -C /var/lib invoice-sorting
sudo systemctl start invoice-sorting
```

不能停服务时，用 SQLite 的在线备份命令分别备份数据库，再复制文件目录：

```bash
sudo -u invoice sqlite3 /var/lib/invoice-sorting/control.db \
  ".backup '/var/lib/invoice-sorting/备份/control_$(date +%Y%m%d).db'"
sudo -u invoice sqlite3 /var/lib/invoice-sorting/invoice.db \
  ".backup '/var/lib/invoice-sorting/备份/invoice_$(date +%Y%m%d).db'"
```

> SaaS 下每个账套的业务库在 `tenants/<账套>/invoice.db`，逐个备份；或直接用 `export-tenant` 导出成搬迁包。

**`secret.key` 必须和数据库一起备份。** 平台邮件（SMTP）密码在库里是用它加密的；恢复时没有原来的 `secret.key`
（或相同的 `INVOICE_SORTING_SECRET_KEY`），邮件密码无法解密，需要在平台后台重新填写。其他数据不受影响。

**SaaS 平台数据库备份（网页）**：平台管理员在运营后台「平台数据库备份」一键备份 `control.db`
（`POST /api/platform/backups`，SQLite 在线备份，服务不停），文件落在 `备份/平台/control_<时间>.db`，保留最近 10 份，可在页面上下载。
它包含全部账套的账号、密码哈希、成员关系、套餐与授权以及加密后的邮件密码——下载后按敏感文件保管，并同时保留 `secret.key`。
各账套的业务数据不在其中，由各账套自己的「立即备份」或 `export-tenant` 负责。单账套部署没有这个入口（接口返回 404）。

Docker 命名卷的备份：

```bash
docker run --rm -v invoice-sorting_invoice-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/invoice-backup-$(date +%Y%m%d).tar.gz -C /data .
```

### 9.3 恢复

```bash
sudo systemctl stop invoice-sorting
sudo rm -rf /var/lib/invoice-sorting
sudo tar xzf /tmp/invoice-backup-20260920.tar.gz -C /var/lib
sudo chown -R invoice:invoice /var/lib/invoice-sorting
sudo systemctl start invoice-sorting
```

只恢复单个账套时，用 `import-tenant --overwrite` 更安全，见[账套搬迁](#八账套搬迁)。单账套换机器只想带走账本与登录账号时，不必复制整个数据目录，按 [8.5](#85-换机恢复单账套) 整套覆盖即可。

## 十、版本与发布

安装脚本**默认按 GitHub Release 安装固定版本**（`CHANNEL=release`）：同一条命令在任何时刻执行，
装到的都是同一份已通过完整 CI 的产物，而不是"当时的 main"。发布物在下载后逐个校验 SHA-256，
校验不过直接中止，不会把半截文件装上去。

### 10.1 版本号策略

- 版本号形如 `v主.次.修`，**唯一权威来源是 `backend/pyproject.toml` 的 `version`**（`uv.lock` 里的同名条目由 `uv lock` 自动同步）。
- 起始版本 **`v0.2.0`**：代表多租户（单账套 / SaaS 双形态）与私有化交付这一代。`v0.1.0` 之前的部署没有 Release，只能走 `CHANNEL=main`。
- 次版本号（`0.X.0`）：新功能、数据库结构新增、部署方式变化。修订号（`0.2.X`）：只修 bug，不改数据结构。
- `1.0.0` 留给对外正式商用。

### 10.2 发布步骤（维护者）

1. 改版本号并同步锁文件：

   ```bash
   # 编辑 backend/pyproject.toml 里的 version = "0.2.0"
   cd backend && uv lock          # 同步 uv.lock 中的项目版本
   ```

2. 提交并打标签（标签必须与 `pyproject.toml` 的版本一致，否则 CI 会直接失败）：

   ```bash
   git commit -am "chore: 发布 v0.2.0"
   git tag v0.2.0
   git push origin main --tags
   ```

3. 推送标签后 `.github/workflows/release.yml` 自动执行：

   | 阶段 | 内容 | 失败后果 |
   | --- | --- | --- |
   | 质量闸门 | 后端 `uv lock --check` + `ruff` + `pytest`；前端 `lint` + `test` + `build`；部署脚本 `bash -n` + `shellcheck` + `deploy/tests/install_env_test.sh` | **不产生 Release**，线上用户不受影响 |
   | 打包 | `backend.tar.gz`（`backend/` 含 `uv.lock` + 顶层 `scripts/`）、`frontend.tar.gz`（`dist/`）、`deploy.tar.gz`、`install.sh`、`manifest.json`、`SHA256SUMS` | — |
   | 发布 | 创建 Release，更新说明由提交记录自动生成 | — |

   也可以在 Actions 页面手动运行「发布版本」，填版本号即可（用于补发或预发布）。

4. Release 出现后，用户执行安装命令即可装到该版本。**不需要**手工上传任何文件。

> 前端预构建 Release `frontend-dist`（`.github/workflows/frontend-dist.yml`）保持不变，
> 它服务于 `CHANNEL=main` 的尝鲜安装；`CHANNEL=release` 用的是版本 Release 里的 `frontend.tar.gz`，两者互不影响。

### 10.3 按版本安装

```bash
# 最新正式版（推荐，日常升级也是这一条）
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh | sudo bash

# 指定版本（固定住，便于复现问题与回滚）
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo VERSION=v0.2.0 bash
```

安装来源相关变量：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `CHANNEL` | `release` | `release`：按版本装发布包（已校验 SHA-256）；`main`：跟随 `main` 分支源码，仅供尝鲜与调试 |
| `VERSION` | 空 | 指定版本，如 `v0.2.0`；留空即最新正式版。**改成旧版本号重跑即为回滚** |
| `ALLOW_MAIN_FALLBACK` | `true` | 没有可用 Release 时回退到 `main` 并在日志里显著告警；生产环境建议设为 `false`，宁可报错也不装不确定的版本 |
| `RELEASE_BASE_URL` | `https://github.com/<仓库>/releases/download` | 发布包下载前缀，可指向内网镜像 |
| `RECREATE_VENV` | `0` | 设为 `1` 时删除旧的 Python 虚拟环境重建（跨大版本回滚后依赖异常时用） |
| `BRANCH` | `main` | 仅 `CHANNEL=main` 生效 |

内网 / 无外网环境：把 Release 的 6 个资产放到内部 HTTP 服务上，按 `<前缀>/<版本>/<文件名>` 摆放，
然后 `RELEASE_BASE_URL=https://内网地址/invoice-sorting VERSION=v0.2.0` 即可。

### 10.4 查看当前版本

```bash
cat /opt/invoice-sorting/VERSION
```

```text
VERSION=v0.2.0
CHANNEL=release
COMMIT=3f2a1c...
INSTALLED_AT=2026-09-20T10:15:00+08:00
```

程序目录里还有一份发布清单 `/opt/invoice-sorting/app/RELEASE.json`（版本、提交、构建时间、各文件 SHA-256）。
每次执行安装命令，日志开头会打印 `版本变更：v0.2.0 → v0.2.1`，末尾的摘要里也有当前版本。

### 10.5 校验和验证

安装脚本会自动对 `backend.tar.gz`、`frontend.tar.gz`、`deploy.tar.gz`、`manifest.json` 逐个比对
`SHA256SUMS` 中的 SHA-256，不一致立即终止并提示"下载被截断或文件被篡改"。想手工复核：

```bash
ver=v0.2.0
base=https://github.com/lsgoodlionel/Invoice-sorting/releases/download/$ver
mkdir -p /tmp/rel && cd /tmp/rel
for f in SHA256SUMS manifest.json backend.tar.gz frontend.tar.gz deploy.tar.gz install.sh; do
  curl -fL --retry 5 -o "$f" "$base/$f"
done
sha256sum -c SHA256SUMS      # 全部 OK 才可信
```

> `SHA256SUMS` 与发布物由同一次 CI 生成并上传，能防下载损坏与传输中被替换，但不等于数字签名。
> 对完整性要求更高的场景，请自行校验 Release 页面的来源与发布者。

## 十一、升级与回滚

### 11.1 升级

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh | sudo bash
```

默认装**最新正式版**（见[版本与发布](#十版本与发布)）。脚本做的事：
停服务 → 备份 `invoice.db` 与 `control.db` 到 `数据目录/备份/`（各保留最近 10 份）→
下载发布包并校验 SHA-256 → 整体替换程序目录（保留已装好的 Python 虚拟环境）→ 按 `uv.lock` 装依赖 →
清理遗留的字节码缓存并重新编译、试导入 → 写 systemd 与 Nginx（沿用已有的形态与授权配置）→
清掉上次的失败状态 → 启动并健康检查。

日志里会打印 `已安装版本：…` 与 `版本变更：旧 → 新`，升级前后各是哪个版本一目了然。

数据目录、systemd 里的形态与授权配置、登录密码都不受影响；
老的单账套部署升级后：自动创建 `control.db`，把原来的用户迁到控制库（id 与密码不变），业务库原地不动，用户无感。

> 从旧版本（用 git 方式装的，`/opt/invoice-sorting/VERSION` 不存在）升级过来不需要任何额外操作：
> 脚本会把程序目录整体换成发布包内容，数据目录与虚拟环境保持不动。

### 11.2 回滚

控制库是**新增文件**，业务库结构没有破坏性改动，因此可以直接回退到旧版本。
**回滚就是指定一个旧版本号重跑安装命令**：

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo VERSION=v0.1.0 bash
```

先确认有哪些版本可选：`https://github.com/lsgoodlionel/Invoice-sorting/releases`，
或在服务器上 `cat /opt/invoice-sorting/VERSION` 看当前装的是哪个。

跨版本回滚后如果后端导入报依赖错误（虚拟环境里留着新版本的包），加上重建虚拟环境重跑一次：

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo VERSION=v0.1.0 RECREATE_VENV=1 bash
```

如果数据也需要回退，用升级前那份自动备份：

```bash
sudo systemctl stop invoice-sorting
sudo -u invoice cp /var/lib/invoice-sorting/备份/upgrade_20260920_101500.db /var/lib/invoice-sorting/invoice.db
sudo -u invoice cp /var/lib/invoice-sorting/备份/control_upgrade_20260920_101500.db /var/lib/invoice-sorting/control.db
sudo systemctl start invoice-sorting
```

> 回退旧版本后，新版本产生的新数据可能无法识别，请优先回退到升级前的备份。

## 十二、故障排查

### 12.1 服务起不来

```bash
sudo systemctl status invoice-sorting
sudo journalctl -u invoice-sorting -n 100 --no-pager
```

常见原因：

| 日志特征 | 原因与处理 |
| --- | --- |
| `bad marshal data` / `marshal data too short` | Python 字节码缓存损坏，见 [12.2](#122-bad-marshal-data字节码缓存损坏) |
| `start request repeated too quickly` | 服务在反复崩溃重启，已被 systemd 限速停下。先看上一次真正的错误，修复后 `reset-failed` |
| `Address already in use` | 端口被占用。换端口重装：`| sudo APP_PORT=18766 bash` |
| `Permission denied` 且路径在数据目录 | 属主不对：`sudo chown -R invoice:invoice /var/lib/invoice-sorting` |
| `database is locked` | 有另一个进程在写同一个库。确认没有重复启动的实例或未退出的命令行任务 |

服务因反复失败被限速停下时（5 分钟内失败超过 5 次），修好之后这样恢复：

```bash
sudo systemctl reset-failed invoice-sorting
sudo systemctl start invoice-sorting
```

Docker：

```bash
docker compose logs --tail 100 app
docker compose ps        # 看 health 状态
```

容器启动就退出并提示数据目录不可写，说明宿主机挂载目录属主不对：

```bash
sudo chown -R 10001:10001 /srv/invoice-sorting
```

### 12.2 `bad marshal data`（字节码缓存损坏）

**表现**：服务启动即崩溃，日志里是 `ValueError: bad marshal data (unknown type code)` 或
`EOFError: marshal data too short`，报错文件通常指向某个第三方包（例如 `openpyxl`）。
systemd 不停拉起又不停崩溃，`systemctl status` 里的 restart 次数飙到几百次，
Nginx 因为后端没起来而返回 **502**。

**原因**：Python 会把 `.py` 编译成 `.pyc` 缓存。如果在写缓存的过程中进程被杀、磁盘写满或断电，
就会留下半截的 `.pyc`；之后每次导入都读到这个坏文件，必然失败。升级时旧服务一边反复重启一边
被替换依赖，最容易踩到。**代码和数据都没坏，删掉缓存就能恢复。**

**恢复**（30 秒）：

```bash
sudo rm -rf /var/cache/invoice-sorting/pycache/*
sudo systemctl reset-failed invoice-sorting
sudo systemctl restart invoice-sorting
```

老版本（缓存还散落在程序目录里）再补一条：

```bash
sudo systemctl stop invoice-sorting
sudo find /opt/invoice-sorting/app/backend -name __pycache__ -type d -prune -exec rm -rf {} +
sudo systemctl start invoice-sorting
```

清完缓存仍然起不来，说明是依赖本身缺失或损坏，重新执行一键安装命令即可修复（数据不受影响）：

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh | sudo bash
```

**现在已经做的防护**（新版安装脚本自动配置，升级一次即生效）：

- 字节码缓存集中到 `PYTHONPYCACHEPREFIX=/var/cache/invoice-sorting/pycache`，
  不再散落在程序目录，**整目录删掉就是完整清理**。
- systemd 的 `ExecStartPre` 每次启动前跑一次导入自检（`deploy/startup-check.sh`）：
  发现导入失败就自动清空缓存再试一次，通常无需人工介入。自检失败也不会阻塞启动。
- 服务非正常退出时，`ExecStopPost` 会在日志里打印排查步骤，并生成一份脱敏诊断包（见 [12.7](#127-运行日志与诊断包把现场交给开发)）。
- `RestartSec=5` + 5 分钟内最多重启 5 次：崩溃循环会被限速停下，不会再刷出几百次重启记录。
- 安装/升级时清理遗留的 `__pycache__` 并用新的缓存目录重新编译、试导入。

查看当前缓存目录与体积：

```bash
sudo du -sh /var/cache/invoice-sorting/pycache
sudo systemctl cat invoice-sorting | grep PYTHONPYCACHEPREFIX
```

### 12.3 界面提示“只读”

先看「设置」页的授权状态（接口 `GET /api/license/status`），按提示判断：

| 提示 | 含义 | 处理 |
| --- | --- | --- |
| 授权已过期，处于宽限期 | 令牌过期但还在宽限天数内 | 联系供应商续期；顺便确认服务器能访问授权服务 |
| 超过宽限期，已切换只读 | 长期没校验成功 | 续期后点「重新检查」，或重启服务 |
| 密钥无效或已停用 | 控制面把这条授权停用了，或密钥填错 | 与供应商核对密钥；确认没有把同一密钥用在两台机器上（换机需平台管理员解绑） |

排查网络：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://saas.example.com/api/health
sudo systemctl cat invoice-sorting | grep INVOICE_SORTING_LICENSE
```

只读模式下**数据不会丢**，查看、导出与备份都还能用。先把数据导出来再处理授权也完全可以。

### 12.4 额度超限（SaaS）

套餐额度触发时，写操作会被拒绝并给出明确文案：

| 提示方向 | 含义 | 处理 |
| --- | --- | --- |
| 不能再添加成员 | 用户数达到套餐上限 | 运营后台升套餐，或停用不再使用的成员 |
| 不能再上传文件 | 存储达到上限 | 升套餐，或清理回收站与历史资料包 |
| 不能再新建记录 | 当月新增记录达到上限 | 升套餐，或等下个月（按自然月计） |
| 账套已停用 / 已过期 | 账套状态不是「正常」 | 运营后台恢复状态或延长到期日 |

### 12.7 运行日志与诊断包（把现场交给开发）

设计见 [运行日志与故障上报 · 设计](日志与故障上报_设计.md)。

**日志在哪**

| 位置 | 内容 |
| --- | --- |
| `<数据目录>/日志/app.log` | 应用日志，按 5 MB × 5 份轮转 |
| `<数据目录>/日志/诊断包/` | 诊断包 zip，只保留最近 10 个 |
| `journalctl -u invoice-sorting` | systemd 记录的启动与崩溃 |

日志里**不会**出现请求体、文件内容、密码、会话 Cookie 与授权密钥；4xx（用户操作反馈）不进错误日志。

**手工生成诊断包**

```bash
sudo -u invoice /opt/invoice-sorting/app/backend/.venv/bin/invoice-sorting diagnose --reason=manual
```

命令会打印包路径。退出码：`0` 成功，`1` 生成失败，`2` 包已生成但上传失败。
管理员也可以在接口里生成：`POST /api/diagnostics/collect`，状态查询 `GET /api/diagnostics/status`。

**包里有什么、脱敏到什么程度**

`summary.json`（版本、形态、Python 与系统、磁盘内存、账套数与记录**数量级**）、`app.log` 尾部、
`journal.log`、`service.txt`、`nginx-error.log` 尾部、`env.txt`（**只写变量名与“已设置/未设置”，不写值**）、
`health.json`。所有文本都会做脱敏：邮箱、手机号、身份证、银行卡、发票号、金额、商家与人名、
公网 IP 与主机名、密钥令牌 Cookie 密码、路径里的用户名都会换成占位符；堆栈的模块路径、
异常类型与行号保留。打包后还会再扫一遍，发现疑似残留就**拒绝上传**并在日志里写明原因。

**默认不上传。** 只有同时配置了日志仓库与令牌才会上传。

#### 启用上传（可选）

第一步，准备一个**私有**仓库（本项目用 `lsgoodlionel/paper`，多个应用共用，按应用分命名空间）。

第二步，创建**细粒度** PAT（Fine-grained personal access token）：

1. GitHub → Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token；
2. **Repository access** 选 *Only select repositories*，只勾 `lsgoodlionel/paper`；
3. **Permissions → Repository permissions → Contents** 选 **Read and write**（其余全部留 *No access*）；
4. Expiration 建议 90 天，到期前轮换；
5. 生成后复制令牌，**只**放进服务器环境变量，不要提交到任何仓库、文档或聊天记录。

第三步，写进 systemd（重新执行安装命令即可，单元文件会自动 `chmod 600`）：

```bash
curl -fsSL https://raw.githubusercontent.com/lsgoodlionel/Invoice-sorting/main/deploy/install.sh \
  | sudo LOG_REPO=lsgoodlionel/paper LOG_TOKEN=<粘贴你的令牌> bash
```

也可以用 drop-in 只放令牌（权限 600）：

```bash
sudo systemctl edit invoice-sorting
```


**关闭上传**：把 `INVOICE_SORTING_LOG_REPO` 清空（重新执行安装命令并传 `LOG_REPO=`），
或删掉 drop-in 后 `daemon-reload` 重启。本机诊断包不受影响。

#### 什么时候会自动上报

| 触发 | 条件 |
| --- | --- |
| 崩溃 | 服务非正常退出，`ExecStopPost` 调用 `diagnose --reason=crash` |
| 运行中错误 | 同一故障指纹（异常类型 + 堆栈顶部位置）10 分钟内累计 ≥ 3 次 |
| 手工 | `diagnose --upload` 或管理员接口 |

限流：同一指纹每天最多 1 次，全实例每天最多 5 次；计数落盘，崩溃重启循环也不会刷爆仓库。
手工生成不受限流影响。

#### 开发侧怎么取

拉取私有仓库后：

```
invoice-sorting/latest.json                       最近一次故障的指纹、版本、时间与包路径
invoice-sorting/logs/<实例名>/<YYYY-MM-DD>/diag_*.zip
```

先看 `latest.json` 定位，再解压对应的包，看 `summary.json` 与 `journal.log`。

#### 令牌安全

- 令牌只从环境变量读，**不落库、不写日志、不进诊断包、不进任何错误信息**；
- 权限最小化（单仓库 Contents 读写），随时可在 GitHub 吊销；
- 建议每 90 天轮换一次；怀疑泄漏时先在 GitHub 删除该 token，再重新生成并更新环境变量。
