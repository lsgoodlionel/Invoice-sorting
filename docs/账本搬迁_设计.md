# 账本一键导入导出 · 设计

编制日期：2026年9月21日

## 1 目标

把一个账本（记录、附件原件、分类与项目、凭证清单、批次、时间线）整体打包带走，并导入到**另一个账户、另一个账套、另一台服务器**——本地部署与 SaaS 部署之间双向可搬。

已有能力（v0.2.0）：`export-tenant` / `import-tenant` 命令行，按**账套整体替换**。本次在其之上补两件事：

1. **合并导入**：并入一个已经有数据的账本，自动去重，不覆盖已有内容。
2. **网页一键**：设置页直接导出下载、上传导入，普通管理员不用登服务器。

## 2 包格式

沿用现有搬迁包（`manifest.json` + `data/` 下的数据库与文件库），新增 `ledger.json` 描述导出范围与来源：

```json
{
  "kind": "ledger",
  "has_accounts": true,
  "source": {"deployment": "saas|single", "tenant": "客户甲", "exported_by": "张三", "app_version": "0.2.1"},
  "scope": {"records": 1234, "attachments": 3456, "batches": 12, "from": "2024-01-01", "to": "2026-09-21"}
}
```

旧包（没有 `ledger.json`）仍可导入，按整账套包处理。`has_accounts` 缺省为 `false`。

### 2.1 登录账号（accounts.json，仅单账套）

**单账套部署**（`deployment_mode=single`）导出时（网页「备份并下载」、命令行 `export-tenant`、覆盖前的自动备份）
在包里加入 `data/accounts.json`，与数据库一样列在 `manifest.json` 的文件清单里、参与逐字节 SHA-256 校验
（清单分节 `sections.accounts`），`ledger.json` 的 `has_accounts` 为 `true`：

```json
{
  "kind": "accounts", "version": 1, "tenant": "default",
  "accounts": [
    {"id": 1, "username": "admin", "display_name": "管理员", "role": "admin",
     "is_active": true, "source": "", "password_hash": "scrypt$n=16384,r=8,p=1$<盐>$<摘要>"}
  ]
}
```

- 内容：该账套**全部成员**的账号 id、用户名、显示名、角色、启用状态、来源标记（`import` 为占位账号）与**原样的密码哈希**（未设密码为 `null`）。
- **不含**：明文密码、登录会话、邀请码、平台管理员标记、授权、邮件设置与 SMTP 密码、`secret.key`，以及其他任何控制面数据。
- **SaaS 部署的账套备份不含账号**（账号是平台共用的），`has_accounts` 为 `false`。
- 导入端把它当作不可信输入：限 16 MB、最多 1 万个账号，逐字段校验类型与取值（用户名须为规范小写、角色只能是 admin/member、
  哈希只能是可见 ASCII 且不超过 255 字符），id 或用户名重复即拒绝；内存中读取，不落盘。
- 日志与报告只出现账号个数与用户名，**绝不出现密码哈希**；内部数据结构的 `repr` 也不含哈希。
- 包因此属于敏感文件：备份页面在单账套部署下提示“备份文件包含登录账号与密码哈希，请当作敏感文件妥善保管”。

## 3 导入模式

| 模式 | 语义 | 入口与保护 |
| --- | --- | --- |
| **合并**（默认） | 把包里的内容并入目标账本，已存在的跳过 | 网页与命令行；导入前先给预览 |
| **覆盖** | 目标账本整体替换为包内容 | 需勾选并输入账套名二次确认；执行前自动整包备份到 `备份/` |

两种模式都在导入前生成**预览**（dry-run）：将新增多少记录与附件、跳过多少重复、有哪些冲突需要人工确认；用户确认后才真正写入。

### 3.1 登录账号的恢复

只有「**整套覆盖**（replace）」且**目标是单账套部署**时才恢复包内 `accounts.json`；其余情况一律不动账号：

| 情形 | 行为 | 报告 |
| --- | --- | --- |
| 单账套 + 覆盖 + 包内有账号 | 按下列规则恢复 | `accounts` 分区 + 顶层 `accounts.will_restore = true` |
| 合并（任何部署） | 不导入账号，人仍按 4.3 匹配或建停用占位账号 | 顶层 `accounts.note`：“包内含 N 个账号，合并模式不导入账号” |
| SaaS + 覆盖 | 不导入账号（账号是平台级的） | 顶层 `accounts.note`：“包内含 N 个账号，SaaS 部署的账号由平台统一管理，覆盖模式不导入账号” |
| 旧包 / SaaS 导出的包（没有 accounts.json） | 与以前一样 | 无 `accounts` 字段 |

恢复规则（按**用户名**对位）：

- **同名的本地账号**：密码哈希、显示名、角色、启用状态改为备份中的值（平台管理员标记、创建时间保持本地原样）；
- **备份有、本地没有**：新建，并使用备份里的账号 id；
- **本地有、备份没有**：**删除**，让恢复后的账号与备份时完全一致；例外是**执行这次恢复的管理员本人**（网页导入时的当前登录账号）
  即使备份里没有也保留。命令行没有登录身份，本账套里备份没有的账号全部删除。不属于本账套的账号（单账套下不存在）不删。
  删除语义与“用户管理 → 删除用户”一致，复用 `users/deletion.py`：控制库删除账号、成员关系与会话，
  其他表里指向它的可空引用置空；业务库 `app_user` 镜像行**保留**并标记 `is_active=false`、`is_deleted=true`、`deleted_at`，
  历史记录仍显示原姓名（新业务库来自备份，按用户名找到镜像行再标记）；已删除的镜像行不再参与启动时的账号迁移，不会被“复活”。
- **会话**：新建、被删除与任何字段被改动的账号，其登录会话全部失效——包括执行导入的管理员本人（若他的密码被恢复，导入后需用备份时的密码重新登录）。
  没被改动的账号会话保留。

**id 对齐**（保证业务库镜像的不变量 `User.id == Account.id`）：覆盖模式下业务库整体换成备份里的库，其中 `app_user.id` 就是备份时的账号 id，
因此恢复的账号**一律以备份里的 id 为准**：

1. 同名账号的本地 id 与备份不同 → 改成备份的 id；
2. 备份里的 id 被一个**保留下来的本地账号**（执行者本人）占着 → 这个本地账号让位（被删除的账号不必让位，先删除再对齐）：若新业务库里有与它同名的用户，就对齐到那个 id（历史记录随之归位）；
   否则换到一个全新的 id（比本地、备份与新业务库里出现过的所有 id 都大）；
3. 保留账号的 id 若在新业务库里属于另一个用户名，同样让位（避免镜像把别人的历史记录改成它的名字）。
   新业务库里的 `app_user` 同样按不可信输入处理：id 不在 1–2³¹−1、用户名不合规的行不参与对齐与新 id 分配。

改 id 时同步改写控制库里所有引用 `account.id` 的外键列（成员关系、会话、邀请、注册申请、邮件设置等，按元数据自动发现），
先挪到负数暂存位再落到目标位，避免交换时撞主键；外键检查推迟到提交时。之后按控制库成员关系补齐业务库镜像。

**至少一个可用管理员**：恢复后本账套里必须至少有一个“启用中且设置了密码”的管理员（内置 `admin` 尚未设密码时可走首次设置，也算可用），否则：

- **解包前**就用只读规划检查，不满足即中止：“恢复后将没有可用的管理员账号（需启用中且已设置密码），已中止导入……”，此时**没有写入任何数据**，也没做覆盖前备份；
- 解包后写回账号在**一个控制库事务**里完成，提交前再复核一次；事务内任何失败（含复核不通过）都回滚控制库，
  并用覆盖前的整包备份把数据库与文件库还原，报告“恢复登录账号失败，账套数据已回滚到覆盖前的状态，登录账号未改动”；
  导入前目标还没有数据库（没有覆盖前备份，例如导入为新账套）时，则撤掉本次解出的数据库、文件库与资料包，回到“什么都没导入”。

预览（`complete` 带 `mode=replace`、命令行 `--mode replace --dry-run`）的 `accounts` 分区逐个列出账号：`added` 新建、
`updated`（原因为“更新密码（恢复为备份时的密码）”“更新显示名、角色或启用状态”“账号编号与备份对齐”）、`deleted`（备份里没有的本地账号，删除；分区多一个 `deleted` 计数）、`skipped`（与本地一致 / 执行导入的管理员本人，保留），
并给出醒目警告：“同名账号的密码将恢复为备份时的密码；执行导入的管理员若在其中，导入后需用备份时的密码重新登录；本地多出的账号将被删除（执行导入的管理员本人除外）”。
若按规划恢复后没有可用管理员，预览的 `warnings` 里提前说明导入会被中止。

## 4 合并规则

### 4.1 去重

| 对象 | 判重依据 | 命中后 |
| --- | --- | --- |
| 附件 | `file_key`（文件内容哈希，已有字段） | 跳过文件与数据库行，沿用本地已有附件 |
| 发票 | 发票号码 | 视为同一张发票，不重复导入 |
| 记录 | 同发票号；或（金额 + 支出日期 + 商家）且附件集合有交集 | 跳过，并在报告中列出 |
| 分类 / 经费项目 | 名称（去空格） | 复用本地同名项；勾选「同时导入系统设置」时分类的颜色、关键词、办理路径以包为准 |
| 凭证规则 / 关键词 / 分类记忆 | 内容相同即跳过；冲突时默认**以包为准**（见 4.5），不勾选则**保留本地** | 报告中列出改写或未采纳的项 |

### 4.2 标识重映射

包内所有主键在导入时重新分配，按旧 → 新映射表改写外键（附件、发票与凭证数据、清单项、时间线、批次成员、导出记录）。**绝不沿用包内的 id**，避免与本地冲突。

### 4.3 人

包里的上传人与操作人按**用户名**匹配本地账号：匹配到就用本地账号；匹配不到则创建一个**停用状态**的占位账号（保留姓名，不能登录），使历史记录仍显示"谁传的、谁改的"。占位账号在用户管理里标注来源为导入。

### 4.4 批次与资料包

- 批次连同成员关系一起导入；名称冲突时追加来源后缀（如"2026-09 第1批（来自 客户甲）"）。
- 已生成的资料包 ZIP **不导入**（可随时重新生成），只保留生成记录。

### 4.5 同时导入系统设置（include_settings）

导入请求（网页 `complete` / `confirm`、命令行 `import-tenant`）带 `include_settings`，**默认 true**。
为 true 时合并模式下以下内容**以导入包为准**，报告中动作记为「更新」（`updated`）：

| 内容 | 规则 |
| --- | --- |
| 用户设置（报告 `settings` 分区「系统设置」） | 只认白名单：`buyer_name` 报销抬头、`buyer_tax_id` 买方税号、`local_region` 本地地区、`detail_platforms` 已带明细平台、`overdue_days` 超期提醒天数。只导入包里实际保存过的键（包里没设过的不清空本地）；取值按设置页规则校验，不合法记为失败并保留本地。明细为「中文名：原值 → 新值」 |
| 同名分类 | 颜色、关键词、办理路径说明改为包内的值；名称、排序、归档状态不动 |
| 凭证规则 | 按「分类 + 附件类型」对位：包内某位的规则与本地同位规则不同 → 本地该位整体替换为包内的；包里有而本地没有的位新增；包里没有的位不动 |
| 分类记忆 | 同一商家/商品本地记为别的分类 → 改为包内的分类；本地独有的记忆保留 |

- **永不导入**：内部版本标记（`keywords_version`、`rules_version`、`classification_memory_version` 等 `*_version`）、
  旧版密码哈希，以及任何与本机路径、部署、认证、授权、日志相关的配置——白名单之外的键一律忽略。
- 地区设置改变后，导入提交后自动重算未完成记录的凭证清单（与设置页保存地区效果一致；重算失败不回滚导入，只提示）。
- 为 false 时保持原行为：冲突保留本地；`settings` 分区把差异列为「跳过」，便于用户决定要不要勾选。
- **覆盖模式**整体替换数据库，设置本来就以包为准，`include_settings` 不起作用；预览与结果的提示中写明这一点。

## 5 网页入口

「设置 → 备份与搬迁」（管理员可见）。**备份即导出，只有一个按钮**；原「数据库快照」已移除，避免两种备份让人困惑
（升级脚本在升级前自己用 `sqlite3` 备份数据库，不受影响）：

- **立即备份（导出）**：一键生成完整包（整个业务数据库，含系统设置、分类、规则与记忆 + 全部附件 + 可选的资料包），
  后台打包，完成后下载到本机；同一个包同时留在服务器上**该账套自己的** `备份/账本备份/`（单账套即 `数据目录/备份/账本备份/`，
  SaaS 为 `tenants/<账套>/备份/账本备份/`），按账套各自保留最近 10 份，可在页面上列出并再次下载
  （`GET /api/backup/packages`、`GET /api/backup/packages/{name}`）。每个包旁边的同名 `.json` 侧车记录是否含资料包、文件数与导出人。
  平台后台替某账套导出的包仍放在平台根目录 `备份/租户导出/`，不进账套自己的列表。
  升级前网页导出的旧包留在 `备份/租户导出/`，不自动迁移，需要可手动移动到 `账本备份/`。
- **单账套的备份带账号**（2.1）：包内含登录账号与密码哈希，页面提示当作敏感文件保管；换机器时在新机器上
  “清空后整套覆盖”即可把账号与密码一起带回（3.1）。合并导入不导入账号。SaaS 的账套备份不含账号，
  SMTP 密码、`secret.key` 等仍不在任何账本备份里。
- **SaaS 平台数据库**（`control.db`）由平台管理员在运营后台单独备份（`/api/platform/backups`），存放在平台根目录 `备份/平台/`；
  单账套部署没有这个入口。
- **导入**：选择文件 → **分片上传**（每片 8 MB，显示进度，支持失败重试该片）→ 服务端合并校验 → 预览（可切换「同时导入系统设置」）→ 确认后执行 → 结果报告（新增/更新/跳过/失败明细，可下载）。
  切换到「清空后整套覆盖」时按覆盖模式重新预览：单账套下显示「登录账号」分区与醒目的橙色警告；
  合并预览里包含账号时只显示一句“合并模式不导入账号”。
- 上传的临时分片放在 `data_dir/.导入暂存/`，超过 24 小时未完成自动清理。

## 6 命令行

```
invoice-sorting export-tenant [--slug x] [--out x.zip] [--no-packages]
invoice-sorting import-tenant --in x.zip [--slug y] [--mode merge|replace] [--dry-run] [--no-settings]
```

`--no-settings` 等同网页取消勾选「同时导入系统设置」。

单账套下 `export-tenant` 同样带上 `accounts.json`（打印“包内含登录账号与密码哈希……请妥善保管”）；
`import-tenant --mode replace` 按 3.1 恢复账号，报告多一行“登录账号：新建 N、更新 N、不变或保留 N”与“账号：…”说明；
合并模式与 SaaS 目标只打印“不导入账号”的说明。

`--mode` 默认 `merge`；`--dry-run` 只输出预览报告不写入。原有行为（整套替换）等价于 `--mode replace`。

## 7 安全

- 包来自外部，一律视为不可信输入：沿用现有 zip 防护（防目录穿越、成员数与体积上限、逐文件 SHA-256 校验），并且**只解包 manifest 列出的成员**。
- 合并导入只按白名单导入用户设置（4.5，可关闭）；认证配置、授权、日志与部署相关配置、内部版本标记一概不动。
- 备份包的列表与下载只看当前账套自己的目录，文件名按白名单正则校验并确认解析后仍在该目录内，其他一律 404。
- 导入需要管理员权限；SaaS 下只能导入**当前账套**，跨账套导入走平台后台。
- 覆盖模式二次确认 + 自动备份；导入过程先写暂存再整体切换，失败不留半个账本。
- 导入报告不包含令牌、密码等敏感信息；账号清单只在内存里读取，日志与报告绝不出现密码哈希。
- 账号恢复只在单账套整套覆盖时发生，权限（管理员）、只读守卫、二次确认与自动备份与覆盖模式相同；
  篡改过的 accounts.json 因校验和不符被拒绝（包括等长改写，例如把成员改成管理员）。

## 8 限制

- 单包上限 2 GB（再大建议在服务器上用命令行）。
- 合并导入不改变本地已有**记录**的任何字段，只做新增；设置类内容可按 4.5 以包为准；整本以包为准时用覆盖模式。
- 跨版本：包的 schema 版本高于当前程序时拒绝导入并提示先升级。
