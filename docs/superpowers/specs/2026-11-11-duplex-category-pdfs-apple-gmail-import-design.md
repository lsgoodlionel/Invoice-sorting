# 双面打印、分类 PDF 与 Apple Gmail 多回执导入设计

## 背景

当前资料包只生成一份合并打印 PDF，无法为双面打印保证每条报销记录从纸张正面开始，也没有按分类拆分的打印文件。现有 Apple 凭证识别器按“一个文件对应一条凭证”处理；Safari 从 Gmail 打印出的 Apple 购买邮件线程可能包含多张回执，因此只会识别第一张，并可能把 Gmail 页眉日期误当成购买日期。

## 目标

- 资料包导出时允许用户选择是否按双面打印规则补空白页，默认关闭并保持现有行为。
- 保留一份合并打印 PDF，同时在 ZIP 中增加按分类拆分的多份 PDF。
- 双面打印模式下，每条记录的下一条记录从正面开始，最后一条记录不增加无意义的尾部空白页。
- Apple Gmail 多回执 PDF 按 `Order ID` 拆成独立导入项，并正确识别购买日期、金额、币种、商品名称、订单号和文档号。
- 每条 Apple 回执沿用现有导入分组、分类建议、清单生成和归属确认流程。
- 原始 Gmail PDF 只保存一份，并可从拆分后的回执追溯来源文件和页码范围。
- 完成后更新项目文档、GitHub、Obsidian 和 `v0.2.8` Release。

## 方案比较

### 资料包 PDF

1. **统一分页计划（采用）**：先把每条记录转换成页序列，再由同一构建器生成合并 PDF 和分类 PDF。排序、附件顺序和双面补页只实现一次，输出之间最不容易出现差异。
2. 先生成 PDF 再做后处理：对合并结果重新扫描边界并补页、拆分类。实现看似独立，但生成后已丢失清晰的记录边界，容易重复解析和错位。
3. 合并版与分类版分别实现：改动直接，但会复制排序、分页和补页逻辑，长期维护风险高。

### Apple 多回执 PDF

1. **导入前拆分为来源文档和逻辑子文档（采用）**：检测 Apple Gmail 邮件线程，定位回执边界，生成每个订单的子 PDF，并记录来源关系。符合现有“一附件一凭证”的模型，同时保留追溯能力。
2. 只增强现有识别器：仍然只能返回一条 `RecognizedEvidence`，无法为多个订单分别生成清单和归属。
3. 一个附件绑定多个订单：需要把附件与支出从一对多改成多对多，影响下载、移动、删除和资料包导出等大量既有逻辑，超出本次必要范围。

## 资料包导出设计

### 接口和界面

导出界面在现有布局选项旁增加“适合双面打印”开关，默认关闭。前端导出请求增加 `duplex: boolean`；后端请求模型也增加同名字段并以 `false` 为默认值，保证旧客户端兼容。

现有布局选择继续决定原始材料在 ZIP 中的组织方式，不影响新增的打印 PDF 输出。

### 统一分页计划

打印 PDF 构建器接收已按分类和日期排序的 `PackageItem` 列表，逐条记录解析可打印附件并形成记录级页序列。每条记录内的附件顺序沿用现有规则。

启用双面打印时：

1. 统计当前记录实际写入的页数；
2. 如果当前记录不是该输出文件中的最后一条，并且页数为奇数，则追加一张 A4 空白页；
3. 最后一条记录无论奇偶都不补尾页；
4. 没有可打印页面的记录不补空白页。

合并 PDF 对全部记录执行一次分页计划。每份分类 PDF 只对本分类的记录独立执行，因此分类文件之间不会相互影响补页结果。

### ZIP 结构和命名

保留现有文件：

```text
00_报销汇总表.xlsx
01_打印版_全部材料.pdf
```

新增目录：

```text
02_按分类打印/
  01_差旅费.pdf
  02_办公费.pdf
  03_未分类.pdf
```

分类文件按分类配置顺序编号，未分类置后。文件名使用现有安全命名规则处理非法字符和重名。分类 PDF 内按消费日期、记录 ID 稳定排序，与合并 PDF 的相对顺序一致。没有记录的分类不生成空文件。

## Apple Gmail 多回执导入设计

### 检测与拆分

在普通发票解析和凭证识别之前增加复合文档检测器，只处理满足以下特征的文本型 PDF：

- Gmail 打印页面或标题包含 `Gmail - Your purchases from Apple`；
- 文本包含 Apple 回执标记和至少一个 `Order ID`；
- 每个候选块能提取唯一 `Order ID`。

检测器按 PDF 页提取文本，使用 Apple 回执标题和 `Order ID` 确定回执起点，以后续回执起点或文档末尾确定结束位置。跨页回执保留完整连续页。若同一页存在无法安全切分的两个回执，导入流程不猜测裁剪边界，而是返回中文提醒并保留原件待人工处理。

每个回执生成一份子 PDF，名称包含购买日期和 `Order ID`。子 PDF 是实际附件，继续使用现有附件识别、分组、确认、移动和资料包导出流程。

### 来源追溯

新增来源文档记录，保存原始文件名、SHA-256、存储路径、MIME、大小和导入时间。原始 Gmail PDF 只存储一次，不直接归属某条支出。拆分出的附件记录来源文档 ID、起止页码和拆分器版本。

重复导入时先按来源文档 SHA-256 判重。子文档同时按来源页范围和 `Order ID` 判重，防止处理中断后重试产生部分重复记录。删除或移动某条支出的子附件不会删除仍被其他子附件引用的原始来源文档。

### 字段识别与业务流

Apple 回执识别器只在当前回执块内提取字段：

- `Receipt` 后的日期作为购买日期，不读取 Gmail 页眉或打印日期；
- `Order ID` 作为订单号；
- `Document No.` 写入结构化详情；
- 商品行写入商品名称；
- `Total` 写入原币金额和币种；
- 商家统一为 Apple；
- USD 等非人民币订单标记为境外在线消费。

每个订单形成一个独立导入组。分类优先使用现有“商家/商品 → 分类”学习结果，未命中时进入现有待确认流程。人民币报销金额沿用当前汇率或人工确认机制，不在识别器中擅自换算。确认后按现有逻辑创建支出、生成清单并完成附件归属。

单个回执识别失败时，不影响同一来源 PDF 中其他已成功拆分的回执；失败项显示原始文件名、页码范围和中文原因。原始来源文档始终保留，便于重新识别。

## 兼容性与边界

- `duplex` 未传或为 `false` 时，合并 PDF 的页面内容与当前版本一致。
- 新增分类 PDF 不改变汇总表和原始材料目录的现有编号与命名。
- 不把普通单张 Apple 回执强制走多回执拆分；现有单文件识别继续可用。
- 不对图片型或无可靠文本层的 Gmail PDF 猜测拆分；此类文件进入现有待人工处理流程。
- 本次不引入通用邮件线程拆分器，只支持已确认的 Apple Gmail 回执格式，并把边界检测封装为可扩展组件。
- 原始来源文档是追溯材料，不参与资料包打印，避免同一邮件线程被重复打印。

## 验证方案

采用 TDD，先写失败测试，再实现最小改动。

### 后端

- 双面关闭时不补空白页；
- 非最后一条记录奇数页时补一页，偶数页时不补；
- 最后一条记录不补尾页；
- 无可打印页面的记录不补页；
- 合并 PDF 和分类 PDF 独立计算补页；
- 分类目录、编号、排序、未分类和安全文件名正确；
- 导出接口默认值和显式 `duplex` 参数正确；
- Apple 样例按唯一 `Order ID` 拆成多条记录；
- 跨页回执完整，购买日期不受 Gmail 页眉日期影响；
- USD 金额、商品名、订单号和文档号正确；
- 原始来源、页码范围和重复导入判定正确；
- 部分回执失败不阻断其他回执；
- 确认后分类建议、清单和附件归属沿用现有流程。

### 前端与集成

- 双面打印开关默认关闭并正确传参；
- 导出成功、失败和旧接口兼容行为不回归；
- 真实样例完成上传、拆分、确认、归属和资料包导出流程；
- 运行与改动范围匹配的前后端测试、类型检查和 Docker 验证。
