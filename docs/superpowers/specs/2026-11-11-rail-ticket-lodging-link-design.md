# 铁路电子客票自动关联住宿记录设计

## 背景

系统已经支持住宿订单、住宿发票与往来交通凭证的分组和已有记录匹配：交通日期位于入住前 1 天至离店后 1 天，且起点或终点属于酒店所在城市时，可作为该住宿记录的往来交通凭证。

样例 `26339119363000147798-电子发票.pdf` 能识别发票号码、乘车日期、金额和乘客，但无法提取“安吉站 → 上海南站、C3029”。该版式将站名、车次放在一行，两个“站”字单独排在下一行；现有铁路票解析器只支持“站名+站”与车次位于同一文本序列的版式，因此后续住宿关联缺少路线信息。

## 目标

- 正确解析该铁路电子客票版式的出发站、到达站和车次。
- 保留现有标准铁路票版式解析结果，不产生回归。
- 复用现有住宿关联规则，不新增重复的匹配体系。
- 唯一强匹配自动挂接到住宿记录，并满足“往来交通凭证”清单项。
- 多个住宿记录同时满足时只列出候选，不自动归属。
- 没有满足时间和地点条件的住宿记录时保留待归属。
- 与双面资料包、分类 PDF、Apple 多回执功能统一进入 `v0.3.0` Release。

## 方案比较

1. **增强铁路票解析并复用现有住宿匹配（采用）**：补充一种路线版式解析，产出标准 `date/from/to/vehicle/number` 详情，现有 L7 分组、住宿评分、自动确认和清单逻辑继续消费统一数据。改动集中、风险最低。
2. 只按乘车日期匹配住宿：实现简单，但同一时间有多次出差时容易串单。
3. 新增一套模糊住宿关联器：可扩大召回范围，但与现有 L7/M3 规则重复，解释和维护成本高，也更容易误关联。

## 解析设计

铁路票解析器继续优先使用现有标准路线模式：

```text
上海虹桥站 G7 南京南站
```

当标准模式未命中时，再匹配样例中的分行站名模式：

```text
安吉 C3029 上海南
站            站
```

备用模式必须同时满足：

- 同一行存在两个中文站名候选；
- 中间存在合法铁路车次（可选 G/D/C/Z/T/K/L/Y/S 前缀加数字）；
- 后续相邻文本包含两个独立“站”标记；
- 文档已经由铁路电子客票解析器确认，不在普通发票文本中泛化匹配。

解析结果统一写为：

```text
date=2026-09-06
from=安吉
to=上海南
vehicle=train
number=C3029
```

记录摘要为“安吉-上海南 C3029”。站名不保留末尾“站”，与现有城市归一化和 `place_in_city()` 规则保持一致。

## 关联与冲突处理

不改变现有住宿关联边界：

- 乘车日期必须处于 `[入住日期−1 天, 离店日期+1 天]`；
- 出发站或到达站至少一端匹配酒店所在城市；
- 已外发批次、作废或删除记录不作为候选；
- 唯一强匹配由现有自动确认流程挂接；
- 多个候选分数同时满足时只在确认页展示候选，由用户选择；
- 无候选时留在待归属。

挂接成功后，附件类型按现有规则为交通凭证，住宿记录的“往来交通凭证”清单项变为已具备；若支出金额尚未被人工改动，继续沿用现有交通票金额并入逻辑。

## 验证

采用 TDD：

- 用隐私安全的合成文本先证明分行站名版式解析失败；
- 实现备用路线模式后断言出发站、到达站、车次、日期和摘要；
- 现有标准铁路票解析测试继续通过；
- 用用户提供的真实样例做本地验证，但不提交原文件或其中个人信息；
- 集成测试覆盖唯一住宿候选自动归属并满足清单；
- 覆盖多个候选不自动归属、地点不符、日期超窗不关联；
- 运行铁路解析、住宿分组、住宿金额与导入确认相关回归测试。

## 发布

实现验证通过后，更新 README、凭证识别设计与 API/交接文档中的支持范围，并与当前双面打印、分类 PDF、Apple Gmail 多回执升级统一发布 `v0.3.0`。GitHub CI、Release 和 Obsidian 项目记录继续按项目交付闭环同步。
